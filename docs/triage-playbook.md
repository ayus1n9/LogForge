# SOC Tier 1 Alert Triage & Investigation Playbook

This document defines the standardized Standard Operating Procedure (SOP) for SOC analysts triaging and investigating alerts within the **LogForge** SIEM platform.

---

## 1. The 8-Point Investigation Workflow

For every security alert generated by Wazuh, analysts must systematically execute and answer the following 8 questions:

```
[ 1. Alert Identification ] ──> [ 2. Endpoint Context ] ──> [ 3. Identity / User ]
              │                                                     │
              ▼                                                     ▼
    [ 4. Timeline Reconstruction ] ─────────> [ 5. Supporting Log Evidence ]
              │                                                     │
              ▼                                                     ▼
    [ 6. Lateral & Secondary Logs ] ────────> [ 7. Benign vs Malicious Assessment ]
                                                            │
                                                            ▼
                                              [ 8. Actionable Containment ]
```

| Step | Core Question | Analyst Action | Key Fields / Data Sources |
| :---: | :--- | :--- | :--- |
| **1** | **What was detected?** | Identify rule ID, severity level, alert name, and MITRE ATT&CK technique mapping. | `rule.id`, `rule.description`, `rule.mitre.id` |
| **2** | **Which endpoint was involved?** | Determine hostname, IP address, OS type, and agent identity. | `agent.id`, `agent.name`, `agent.ip` |
| **3** | **Which user or process was involved?** | Identify the acting identity (SubjectUser) and affected identity (TargetUser) or process context. | `win.eventdata.targetUserName`, `win.eventdata.user`, `win.eventdata.image` |
| **4** | **When did the activity occur?** | Record initial detection timestamp, duration of activity, and event sequencing. | `@timestamp`, `win.system.timeCreated` |
| **5** | **What evidence supports the alert?** | Extract command-line flags, process hashes, IP/port sockets, or error codes. | `win.eventdata.commandLine`, `win.eventdata.destinationPort`, `win.eventdata.hashes` |
| **6** | **What additional logs should be checked?** | Pivot to Sysmon Process Creation (ID 1), Network (ID 3), DNS (ID 22), or Security (4624/4625). | EventChannel correlation |
| **7** | **Is this Benign, Suspicious, or Malicious?** | Perform hypothesis testing: verify change tickets, scheduled jobs, admin routine vs adversary patterns. | SOC analysis, threat intel |
| **8** | **What defensive action is recommended?** | Provide concrete containment, eradication, and post-incident hardening recommendations. | Host isolation, credential resets, rule tuning |

## 2. Playbook A: Authentication & Account Abuse Alerts

### Target Rules
- **Rule 100101**: Potential password guessing / brute-force (5+ failures in 60s)
- **Rule 100103**: Successful authentication following repeated failed attempts (CRITICAL)
- **Rule 100202**: User added to privileged `Administrators` group

### Step-by-Step Triage Procedure

```
1. Is TargetUser a critical/administrative account (e.g., Domain Admins, local Administrator)?
   ├── YES ──> Escalate priority to P1.
   └── NO  ──> Standard P2/P3 queue.

2. Check Source IP / Workstation:
   ├── Source is 127.0.0.1 or Local Machine: Check for expired scheduled task or local service credential cache.
   └── Source is Remote IP or External: Check if IP is internal corporate subnet or unauthorized network.

3. For Rule 100103 (Failure -> Success):
   - Immediately assume possible compromise.
   - Query all Sysmon Event ID 1 (Process Create) logs under TargetUser from the timestamp of logon success onwards.
   - If interactive commands (e.g. `whoami`, `net group`, `powershell`) were spawned:
     ==> INITIATE CONTAINMENT: Disable user account and isolate endpoint.
```

## 3. Playbook B: Suspicious Process & LOLBIN Execution

### Target Rules
- **Rule 100301**: Suspicious PowerShell execution with download/bypass cradle syntax
- **Rule 100302**: Base64 encoded PowerShell arguments (`-EncodedCommand`)
- **Rule 100305**: LOLBIN established outbound connection on non-standard port

### Step-by-Step Triage Procedure

```
1. Extract and Deobfuscate Payload:
   - For Base64 strings: Decode using CyberChef / Python (UTF-16LE / Unicode).
   - Inspect script content for socket connections, web requests, memory injection, or credential dumping.

2. Inspect Process Lineage (Parent/Child relationship):
   - What spawned PowerShell?
     - Winword.exe / Excel.exe  ==> Malicious macro / Initial access.
     - Cmd.exe / Explorer.exe   ==> Interactive execution or script execution.
     - CcmExec.exe / Lansweeper ==> Likely legitimate administrative deployment.

3. Pivot to Network Activity (Sysmon Event ID 3 / Wazuh Rule 100305):
   - Did the process connect to an external IP or uncommon port (e.g., 4444, 1337)?
   - Cross-reference destination IP against VirusTotal, AbuseIPDB, or Threat Intel feeds.

4. Containment Actions:
   - Terminate offending process tree.
   - Quarantine or hash-block the binary.
   - Review file creation logs (Sysmon Event ID 11) for dropped second-stage tools.
```
